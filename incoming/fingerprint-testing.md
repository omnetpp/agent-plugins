### Ingredient semantics (inet-fingerprint-ingredients.md)
- Fingerprint CSVs store `HASH/INGREDIENTS`. The set tested is `["tplx", "~tNl", "~tND", "tyf"]` (`python/inet/test/fingerprint/task.py`). Plain letters = OMNeT++ kernel ingredients (`omnetpp/include/.../cfingerprint.h`); `~ U N I D` = INET custom (`src/inet/common/FingerprintCalculator.cc`, active when `~` present).
- Letters: `t`=sim-time, `p`=module full path, `l`=msg bit length, `x`=extra module data, `y`=display strings, `f`=canvas figures (`y`/`f` need fake-gui). `~`=NETWORK_COMMUNICATION_FILTER (count only inter-node packets), `N`=sender/arrival **node** full path, `D`=**packet data** (deep contents), `I`=interface path, `U`=packet-update filter.
- `b`=parsim-packed message bytes (`cMessage::parsimPack`), used in `~tNlb` cases (many IPv6/eigrp/mipv6 examples). NOT on-wire data — it **includes the cMessage object NAME** (`cNamedObject` packs `getName()`) plus parsim-serialized fields like `Protocol::getId()`. So a `setName()` rename or inserting a new Protocol moves **~tNlb** while `~tND`/`tplx`/`~tNl` stay put (e.g. renaming ND packets RApacket→RouterAdvertisement moved 14 IPv6 `~tNlb` baselines). Plain `~tNl` (no `b`) does NOT capture the name.
- Interpretation: **tplx** = ALL events incl. internal self-msgs/timers → most sensitive (any scheduling/init-ordering change moves it). **~tNl** = the on-the-wire traffic (which packets, when, lengths). **~tND** = packet contents. **tyf** = graphical/fake-gui (flagged unreliable, often skipped with `-F tyf`).
- Reading a drift: **tplx moved but ~tNl/~tND/tyf identical ⇒ internal event scheduling changed, observable network traffic unchanged ⇒ benign** (e.g. a module made lifecycle-aware reschedules startup). If ~tNl moves, the actual traffic changed.
- Run one ingredient: `bin/inet_fingerprinttest -C $INET_ROOT -s -f tplx <csv>` (`-s`=release, `-f`=ingredient filter).
- `~tND` (and other ingredients) are **checksum-value-independent**: changing a protocol's checksumMode (real vs sentinel) does NOT churn fingerprints; only serialized pcap bytes change. (inet-statistical-tests-tooling.md)
- `~tNl` does NOT force serialization (no checksumMode/fcsMode requirement); only `~tND` does — why ospfv3 `~tNl` fingerprints passed without a serializer existing. `~tND` needs computed fcs+crc+checksum modes (e.g. `**.checksumMode=computed` even for the IPv4 ping in an IS-IS example). (ospfv3-serializer-todo.md, ansa-isis-port.md)
- `tyf` = DISPLAY_STRINGS+CANVAS_FIGURES only (`y`=display strings, `f`=canvas figures, per omnetpp cfingerprint.h). (pmipv6-port.md)
- NED **package/directory rename does NOT move fingerprints** — `tplx` keys off network/module *instance* names, not NED package/file path (confirmed by the examples/pim flattening: 10 fingerprints byte-identical). (inet-pim-examples-cleanup-todo.md)
- **Deleting a submodule from every node legitimately changes ~tNlb**: it renumbers module/event ids, reordering simultaneous events in the hash even when packet behavior is identical (proof it's structural: unrelated pure-IPv6 examples, e.g. nclients/eigrp, also changed). Technique: keep the emptied module as a wired **inert shim** first (fingerprints stay bit-identical → proves the code removal is behavior-preserving), THEN delete the shim and re-record in a separate commit. (mipv6-tunneling-refactor-plan.md)
- If a serializer exists but a protocol's chunkLength is wrong, the chunk serializer PADS with uninitialized bytes → run-to-run `~tND` drift (see Debugging: OSPFv3 case). (ospfv3-tnd-nondeterminism.md)

### Recording / re-recording workflow
- **Purge stale files first**: `rm -f tests/fingerprint/*.UPDATED tests/fingerprint/*.ERROR tests/fingerprint/*.FAILED` before each re-record; then run the suite and trust `grep 'FAILED (should be PASS)' <log>` for what actually changed — NOT a leftover `.UPDATED`. A stale `.UPDATED` from an earlier run/commit produces phantom "fingerprint changed"/"non-determinism" symptoms (a real case cost a long detour chasing a non-existent non-determinism bug; the sim was deterministic — 35 isolation + 3 full runs identical). For determinism doubts, run the suite 2x and compare. (fingerprint-purge-stale-updated.md)
- Re-record with `inet_fingerprinttest <csv> -m <regex>` run from project ROOT (CSV working dirs are relative to cwd); the `.UPDATED` file is a drop-in re-baseline (`cp` over the csv once verified). (mipv6-tunneling-refactor-plan.md, mipv6-new-scenarios-plan.md)
- Record flow for a NEW example: put placeholder hashes `0000-0000/tplx;0000-0000/~tNl` in the csv → `(cd tests/fingerprint; ./fingerprinttest -s babel.csv)` writes `babel.csv.UPDATED` → `cp` to `babel.csv` → re-run = PASS. **CSV sim-time-limit MUST match the ini's.** (ansa-babel-port.md)
- Alternative invocation seen: `PATH=$INET_ROOT/bin:$PATH; ./tests/fingerprint/fingerprinttest -c inet::FingerprintCalculator tests/fingerprint/isis.csv`. (ansa-isis-port.md)
- `run_fingerprint_tests`/`update_fingerprint_test_results` (opp_repl) default to **debug** mode; the chunk-length serializer check is debug-only (release won't crash, silently emits a too-short header). (inet-fingerprint-ipv6-pending.md)
- The `~tNlb` entries live in `mipv6-refactoring.csv`; the 4-ingredient (tplx;~tNl;~tND;tyf) rows in `examples.csv`. (mipv6-new-scenarios-plan.md)
- When touching a shared area, hold the invariant that unrelated fingerprints stay **byte-identical** (e.g. the 8 IPv4 PIM rows when doing IPv6 PIM; the 8 IPv4 bgpv4 rows when doing BGP-IPv6) — design changes specifically to preserve this (e.g. BGP MP capability advertised for IPv6 sessions ONLY, since IPv4 unicast is BGP's implicit default AF; the first attempt advertising on IPv4 too moved all 10 fingerprints and was reverted). (inet-pim-ipv6-state.md, inet-bgp-ipv6-check-todo.md)
- Before blaming your change for a fingerprint mismatch, check whether the baseline is **pre-existing-stale on master**: verify by running a clean checkout WITHOUT your changes and seeing it compute the same "drifted" value (done for mipv6 tyf baselines and BgpCompleteTest ~tND). (pmipv6-port.md, ansa-vrrp-lisp-port.md, inet-bgp-ipv6-check-todo.md)
- Justify fingerprint re-records **per-ingredient** in the commit message (e.g. "~tNl unchanged — only tplx (TCP-command events) + ~tND (ephemeral source-port content) moved"). (inet-bgp-reconnect-graceful-shutdown.md)

### Protocol-registry insertion gotcha (inet-protocol-registry-ppp-fingerprint.md)
- INET `Protocol` objects get a sequential `id` in definition order (`Protocol.cc`). Inserting a new entry alphabetically in the middle (the project convention) renumbers the id of every protocol defined after it (e.g. adding `Protocol::mld` between `manet` and `mobileipv6` shifts `ppp`, `sctp`, `tcp`, `udp`, …).
- `~tNlb` hashes packet content via `parsimPack()`, and a packet's `PacketProtocolTag` serializes its `Protocol` as `protocol->getId()` (`Protocol.h` `doParsimPacking`). An id shift **silently changes `~tNlb` for every PPP-framed example** (PPP frame's PacketProtocolTag is `ppp`, which sorts after most new protocols), while: Ethernet-framed runs are immune (`ethernetMac`/`ethernetphy` sort early); `~tNl`/`tplx`/`tyf` are immune (no parsim serialization); on-wire bytes are unchanged (PPP writes the stable `getPppProtocolGroup()` number, not the id).
- So: adding a Protocol entry ⇒ expect to re-record the PPP `~tNlb` fingerprints (in this repo: `ipv6/nclients` PPP & PPP_SCTP, `inet/udpclientserver` udp_*_ipv6, plus any other PPP example). Legitimate deterministic re-record, not a regression. If a PPP `~tNlb` changes for no apparent reason, suspect a Protocol-registry insertion and `git bisect`.

### Signal-checking asymmetry between harnesses (inet-new-signal-three-steps.md)
- The module-test harness (`python/inet/test/opp.py`) runs every sim with explicit `--check-signals=false` → undeclared/mis-typed signal emits silently tolerated, tests pass.
- The fingerprint harness runs the debug binary (`inet_dbg`) and leaves `check-signals` at its OMNeT++ default = **true in DEBUG, false in RELEASE** → the validator fires and every sim aborts at init → run shows `errors=N` (a crash), not a fingerprint mismatch.
- So: always run the **debug** fingerprint suite when adding signals — it's the only harness with the validator on. (Not about fingerprint sensitivity: a no-subscriber signal records no statistic, all ingredients stay byte-identical.)
